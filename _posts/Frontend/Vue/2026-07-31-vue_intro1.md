# Vue.js의 특징 1 - MVVM Architecture 

Vue.js의 설계는 MVVM(Model-View-ViewModel) Architecture Pattern에서 영감을 받았지만, MVVM을 엄격하게 따르는 것은 아니다.

```text
[Model] ⇄ [ViewModel] ⇄ [View]
              ↑
       Vue의 반응형 연결
```

이게 뭐냐고요? 잘 따라와 보십쇼. 

```text
[궁금증]
   ↓
[MVVM 구조 살펴보기]
```

## Then, what is MVVM?

MVVM Architecture Pattern은 데이터를 보여주는 View와 데이터를 처리하는 Model 사이에 데이터를 중개하는 ViewModel을 두어 UI를 그리는 부분과 Data 처리 로직을 분리하는 Architecture Pattern이다.

```text
[Model: 데이터]
       ↕
[ViewModel: 연결·상태]
       ↕
[View: 화면]
```


### model 

- 애플리케이션에서 사용하는 데이터와 상태. Vue에서는 보통 `<script>` 내부에 정의한 반응형 JavaScript 상태가 이에 해당한다.

```text
[애플리케이션 데이터]
          ↓
 [반응형 JavaScript 상태]
```

### View 

- 사용자에게 실제로 보여지는 화면 인터페이스와 DOM 구조, 시각적 스타일링을 담당

```text
[View]
  ├─ 화면 인터페이스
  ├─ DOM 구조
  └─ 시각적 스타일링
```

### ViewModel 

- View와 Model 사이를 연결해주는 중간 다리. Vue의 반응형 상태·템플릿 연결 로직과 런타임이 ViewModel에 가까운 역할을 수행

```text
[View] ⇄ [반응형 상태·템플릿 로직] ⇄ [Model]
```

### 그러면 어떻게 생긴 걸까?

```text
[Model]
   ⇅
[ViewModel]
   ⇅
[View]
```

## MVVM 구조는 왜 나온 걸까?

근데 대충 어떻게 생겼는지 다들 알았을 것이라 생각한다. 

```text
[Model] → [ViewModel] → [View]
```

그러면 이게 왜 만들어진 것일까? 

```text
[분리된 역할]
      ↓
[변경 관리가 쉬운 구조]
```

1. 기존 브라우저의 Real DOM을 자주 직접 조작하면 렌더링 비용이 커질 수 있다.
- DOM: Browser가 HTML을 인식하여 Tree 구조로 만든 Object Model

```text
[HTML]
  ↓ 파싱
[DOM Tree]
  ↓ 렌더링 계산
[화면]
```

기존 브라우저에서는 실제 DOM이 수정되면 Browser는 Layout을 다시 계산(Reflow)하고 화면을 다시 색칠하는 Repaint 연산을 수행할 수 있다. 이러면 연속적인 상태 변경으로 인해 노드를 재구성하는 작업이 반복되고, Layout/Paint 연산 부하로 화면이 느려질 수 있다.

```text
[DOM 수정]
    ↓
[Layout/Reflow]
    ↓
[Paint/Repaint]
    ↓
[화면 갱신]
```

뭐 예시를 간단하게 들어보자면.. 

```text
[추상적인 설명]
        ↓
   [생활 속 예시]
```

브라우저의 상태가 변경될 때마다 직접 Real DOM을 연속해서 조작하므로, 만약 10번의 데이터 변화가 일어나면 브라우저가 매번 DOM 변경을 처리하고 그 결과에 따라 여러 번의 스타일 계산·Layout·Paint가 발생할 수 있다.

```text
데이터 변화 1 ─┐
데이터 변화 2 ─┤
데이터 변화 … ─┼→ DOM 처리 → Layout/Paint 가능
데이터 변화 10 ─┘
```

실생활에서의 예를 들자면 

```text
[데이터 변경]
      ↓ 비유
[마트를 여러 번 방문]
```

감자 10개를 환불하고 고구마 5개를 사야하는데, 감자 환불 하러 10번 마트가고 고구마 사러 마트 5번 가는 느낌이랄까? 그렇게 예를 들 수 있을 거 같다. 

```text
[감자 환불 10번] + [고구마 구매 5번]
                 ↓
          [마트 방문 반복]
```

2. Vue.js는 Virtual DOM과 렌더러를 통해 필요한 DOM 변경만 적용한다.

- Virtual DOM: 실제 브라우저의 DOM과 동기화되는 메모리상의 UI 표현

```text
[상태 변화]
    ↓
[Virtual DOM 비교]
    ↓
[필요한 Real DOM만 업데이트]
```

아무튼 이런 문제를 줄이기 위해서 Vue.js에서는 Virtual DOM과 렌더러로 변경 사항을 비교한 뒤 필요한 DOM 업데이트를 적용한다.

```text
[이전 Virtual DOM] ⇄ [새 Virtual DOM]
          ↓ 차이 계산
    [필요한 DOM 업데이트]
```

10번 변경할 것을 여러 번의 상태 변경으로 모아서 한 번의 업데이트 사이클에 처리할 수 있게 해준다.

```text
[상태 변경 1]
[상태 변경 2] ─┐
[상태 변경 …] ─┼→ [업데이트 사이클 1회]
[상태 변경 10] ┘
```

개발자가 직접 DOM을 일일이 제어하는 번거로움 없이, 상태 변화만 선언해도 Vue가 반응형 의존성을 추적하고 변경된 Virtual DOM을 이전 것과 비교해 필요한 DOM 업데이트를 계산한다.

```text
[상태 선언]
    ↓
[반응형 의존성 추적]
    ↓
[Virtual DOM 비교]
    ↓
[필요한 DOM 업데이트 계산]
```

Batch 처리를 통한 렌더링 횟수 최적화를 통해 Vue는 한 업데이트 사이클 안에 여러 번 데이터가 바뀌어도 변경 사항을 모아서 실제 DOM에 한 번 반영할 수 있다.

```text
[여러 상태 변경]
        ↓ Batch
[한 번의 업데이트 사이클]
        ↓
   [Real DOM 반영]
```

```text
[상태 변경]
    ↓
[Vue 반응성 + Virtual DOM]
    ↓
[필요한 화면만 갱신]
```

# Vue.js 특징 2 - Two-Way Data Binding

Vue.js에서 `v-model`을 사용하면 양방향 데이터 바인딩 (Two-Way Data Binding)을 구현할 수 있다. "Model(JavaScript Data)이 바뀌면 View(화면)가 바뀌고, 반대로 View(화면 입력)가 바뀌면 Model도 동시에 바뀐다"는 것을 의미한다.

```text
[Model: JavaScript Data]
          ⇅
 [v-model 양방향 연결]
          ⇅
      [View: 입력 화면]
```


# Vue.js 특징 3 - Component Based Architecture

웹페이지를 통째로 만들지 않는다! 

```text
[큰 웹페이지 하나]
        ↓ 분리
[여러 개의 컴포넌트]
```

이제는 조각조각 하나씩 만들고 각각을 조립하는 시스템을 채택한다.

```text
[Header] + [Content] + [Footer]
              ↓ 조립
          [웹페이지]
```

- 이 방식을 Component(독립 요소) Based Architecture라고 한다. 

```text
[Component Based Architecture]
              ↓
 [독립적인 요소를 조립해 화면 구성]
```

세 가지 특징을 가진다. 

```text
[Component]
 ├─ Encapsulation
 ├─ Reusability
 └─ Tree Structure
```

- Encapsulation : Single-File Component(SFC)로 작성하면 컴포넌트의 HTML(구조), JavaScript(로직), CSS(스타일)를 하나의 파일(.vue) 안에 응집시켜 놓는다.

```text
[Component.vue]
 ├─ <template>  구조
 ├─ <script>    로직
 └─ <style>     스타일
```

- Reusability: 잘 만든 Component는 여러 곳에서 다시 가져다 쓸 수 있어 중복 코드가 제거된다. (재탕이 최고!)

```text
       [재사용]
          ↑
[Component] ─┬→ [화면 A]
             └→ [화면 B]
```

- Tree Structure: Component들은 부모-자식 관계를 가지며 부모는 자식에게 데이터를 내려주고(Props Down), 자식은 부모에게 상태 변경을 알려준다(Event Up = Emit).

```text
        [Parent]
        ↙      ↘
 [Child A]   [Child B]
    ↑ Props Down / Event Up ↑
```

# Vue.js 특징 4 - Rendering

근데 이러면 화면은 어떻게 표시되는 걸까? 

```text
[Vue 상태·템플릿]
        ↓ 렌더링
      [화면]
```

HTML은 조상님이 렌더해주시는 걸까? 

```text
[HTML]
  ?
[조상님 렌더링?]
```


그럴 리는 없겠지...?

```text
[조상님]
   ✕
[렌더링 담당 아님]
```

아쉽게도 조상님 대신 콤퓨타가 렌더해준다..

```text
[Vue + Browser + JavaScript]
             ↓
          [렌더링]
```

화면을 구성하는 대표적인 방식은 2가지이다.

```text
          [렌더링 방식]
             ↙   ↘
          [CSR] [SSR]
```

1. CSR(Client-Side-Rendering)
    - 브라우저(Client)가 JavaScript를 실행하여 화면을 직접 그린다(rendering).
2. SSR(Server-Side-Rendering)
    - 서버(Server)에서 Vue 컴포넌트를 HTML로 렌더링해 브라우저에 내려주는 방식이다. 데이터는 서버에서 미리 주입할 수도 있고, Vue의 SSR API나 Nuxt.js 같은 프레임워크를 이용해서 구현한다.

```text
[CSR] 브라우저에서 JavaScript 실행 → 화면 렌더링
[SSR] 서버에서 HTML 렌더링       → 브라우저 전달
```


# Vue.js로 구현하는 SPA (Single Page Application)

자자 아직 할 것이 많으니 다음으로 넘어가자. 

```text
[Vue 특징 1~4]
        ↓
[SPA 방식 살펴보기]
```

Vue.js로 구현할 수 있는 SPA(Single Page Application)에 대해서 알아보자?

```text
[Vue.js]
    ↓ 구현
[SPA]
```

### 기존 : MPA

기존에는 사용자가 메뉴를 클릭할 때마다 새 HTML을 새로 요청해서 렌더했다.

```text
[메뉴 클릭]
    ↓
[새 HTML 요청]
    ↓
[전체 페이지 렌더링]
```

그래서 페이지 전환마다 HTML과 리소스를 다시 요청할 수 있어 네트워크 비용과 처리 시간이 늘어날 수 있었다.

```text
[페이지 전환]
      ↓
[HTML·리소스 재요청 가능]
      ↓
[네트워크·처리 비용 증가 가능]
```

### 신규 : SPA

다행히도! Vue.js로 SPA (Single Page Application)를 구현하면 HTML 문서를 처음에 불러온 뒤, 클라이언트 측 JavaScript가 필요한 데이터와 화면만 업데이트하는 방식으로 변경을 처리할 수 있다.

```text
[HTML 문서 최초 로드]
          ↓
[클라이언트 JavaScript]
          ↓
 [변경된 화면만 업데이트]
```

## 어떻게 구현? 그리고 뭐가 장단점일까? 

구현은 초기 로딩 시 하나의 HTML과 초기 화면에 필요한 JavaScript를 로딩하는 방식으로 이루어진다.

```text
[초기 로딩]
 ├─ HTML
 └─ 초기 화면에 필요한 JavaScript
```

이제 뭔가 변경이 필요하다면 클라이언트에서 JS로 필요한 부분만 변경(부분 렌더링)하는 방식으로 이루어진다.

```text
[변경 요청]
    ↓
[클라이언트 JS]
    ↓
[필요한 부분만 변경]
```

데이터 전송도 필요한 데이터만 주고받고, 클라이언트의 JS로 필요한 부분만 변경(부분 렌더링)한다.

```text
[서버] ⇄ [필요한 데이터]
              ↓
        [클라이언트 JS]
              ↓
       [부분 렌더링]
```

그래서 여러 가지 장점을 제공한다.

```text
[SPA]
 ├─ 빠른 페이지 전환
 ├─ 네트워크 효율성
 └─ 역할 분리
```

1. 페이지 전환 시 전체 문서를 다시 로드하지 않아 빠른 사용자 경험을 제공할 수 있다.
2. 네트워크 효율성 : 한 번 로딩된 리소스 (CSS, JS 등)를 재사용하고 필요한 데이터만 요청할 수 있어 전체적인 네트워크 트래픽을 줄일 수 있다. (엄마가 끓여주신 사골국으로 온갖 요리를 해먹는 것을 생각해보자, 본인은 일주일동안 사골로 사골라면, 사골된장찌개...부터 시작해서 약 10가지 요리를 해봤다..OTL)
3. 프론트/백엔드 분리: 프론트엔드는 Vue 화면과 로직을 담당하고, 백엔드는 API로 데이터를 제공하는 식으로 역할을 나눌 수 있어 개발 팀 간 협업과 서버 구성이 명확해질 수 있다.

```text
[Vue 프론트엔드] ⇄ [API 서버]
   화면·로직          데이터 제공
```

근데 이 방식 장점만 있는 것은 아니다.

```text
[SPA 장점]
    +
[SPA 단점]
    ↓
[상황에 맞는 선택]
```

여러 가지 문제가 있다.

```text
[주의할 점]
 ├─ 초기 로딩
 ├─ 새로고침
 └─ SEO
```

1. 초기 로딩이 느려질 수 있다.
    - 첫 로딩 시 초기 화면에 필요한 JavaScript를 내려받고 실행해야 해서 초기에 느리게 로딩될 수 있다.
2. 새로고침 시 전체 앱이 다시 로딩된다.
    - 이로 인해 상태가 초기화될 수 있다.
3. JS 기반 렌더링만 사용하는 경우 SEO에 불리할 수 있다.
    - 로봇이 들어와도 JavaScript 실행 전에는 알맹이를 못 볼 수 있다.
    - 그래서 검색 노출에 불리할 수 있다.
4. 별도 기술 조합이 필요할 수 있다. 예를 들어 Vue.js + REST API (ex: Spring Boot)를 함께 구성해야 한다.

```text
[SPA 단점]
 ├─ 초기 JavaScript 로딩·실행
 ├─ 새로고침 시 앱 재로딩
 └─ CSR 환경에서 SEO 불리할 수 있음
```

### Vue.js로 SPA를 만들 때 자주 쓰는 추가 기술 요소

- Vite: Frontend Build Tool로 개발자가 작성한 수많은 .vue, .js, .css 파일들을 개발 중에는 빠르게 제공하고, 배포 시에는 브라우저가 읽을 수 있는 최적화된 정적 파일로 변환·번들링하며 개발 서버도 띄워주는 빌드 도구이다.
- Vue Router: 브라우저의 URL 주소와 Vue 컴포넌트를 연결해 주는 공식 라우팅 라이브러리
- Pinia: 전역 상태 관리 라이브러리로 필요한 컴포넌트가 접근할 수 있는 중앙 집중식 데이터 저장소(Store)를 메모리 상에 개설한다.
- Axios: 백엔드 서버(API 서버)와 JSON 등을 주고받는 HTTP 통신 창구.

```text
[Vite]
   ↓ 빌드
[Vue 앱 정적 파일]
   ↓ 라우팅·상태·통신
[Vue Router] + [Pinia] + [Axios]
```

### SPA의 장점 
- 압도적인 사용자 경험(UX)
- 네트워크 효율성 
- 프론트 / 백엔드 분리 

```text
[SPA 장점]
 ├─ 사용자 경험
 ├─ 네트워크 효율성
 └─ 프론트 / 백엔드 분리
```

### SPA 단점 
- 초기 로딩 속도: 초기 화면에 필요한 JavaScript가 한꺼번에 다운로드·실행되면 첫 접속 시 대기 시간이 발생할 수 있다. 코드 분할을 적용하면 필요한 코드만 먼저 불러올 수도 있다.
- SEO 취약: 순수 CSR에서는 검색 로봇이 JavaScript를 실행하기 전 알맹이가 적은 `index.html`을 먼저 보게 될 수 있어 검색 노출에 불리할 수 있다.

```text
[초기 JS 다운로드·실행]
          ↓
   [첫 화면 대기 시간]

[SSR/SSG 또는 코드 분할]
          ↓
   [초기 부담 완화 가능]
```
